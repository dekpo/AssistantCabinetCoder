# Architecture (completed lot by lot)

Status after Lot X1d: the connection layer and the model provider exist and are tested: the server's models appear in the chat and answer in Ask, Agent and Plan. Lot X1c made discovery use the server's always-open loopback listener (D-018). Lot X1d changed the input budget reported to the editor so that a 32768-token model starts Agent and Plan on VS Code 1.147.0 (D-023). Lot X1e made the provider remember, for 30 seconds, a refusal that retrying cannot fix, because the editor retries every failure five times, and gave the window-overflow sentence the server's numbers (D-025). Decision D-026 (23 November 2026) froze the provider at that point: the next lots (P0a, P0b) build a chat panel of the extension's own, with its own agent loop and tools, and reuse every module that speaks to the server; the editor-chat tools and synced agents once planned here are paused. Lot P0a built that panel: a webview view in the right side bar, a plain chat (no tools yet) whose request is sent once and whose **Stop** closes the connection, and conversations saved on the user's machine (D-027); the provider in the editor's chat is still registered, unchanged. Lot P0b gave the panel an agent loop (`agent`) and four workspace tools (`tools`, `workspace`): read a file, list a folder, search text, propose an edit that the editor applies only after the user's click (D-030).

All sources are in `src/`, one job per module, zero runtime dependencies (only `node:` built-ins and the `vscode` types). Machine codes cross module boundaries; sentences exist only in `messages.ts`. Only the two adapters, `extension.ts` and `panel.ts`, import the editor: everything else runs in plain Node and is tested without it. Only `store.ts` writes files (D-027).

## Data flow of one chat request

1. The user sends a message. VS Code calls `provideLanguageModelChatResponse(model, messages, options, progress, token)` on the adapter in `extension.ts`.
2. The adapter changes what the editor's types cannot carry: each role number becomes its **name** (`User`, `Assistant` or `System`: the editor sends a System role that its type declarations do not list), the tool mode becomes `auto` or `required`, the cancellation token becomes an `AbortSignal`, and `progress` is wrapped so that plain parts become `LanguageModelTextPart` and `LanguageModelToolCallPart`.
3. `ChatProvider.chat` calls `convert.buildChatRequest`: roles by name, text parts joined, tool results into `tool` messages (an image of a tool result goes into the following `user` message, preceded by a note naming the tool), images into `image_url` data URLs, tools into function tools (a name the server would refuse is left out and counted), sampling options only when the editor sent a known key. An image for a model without vision, a role or a part that cannot be carried is refused here, **before anything is sent**, with a sentence from `messages` (a `ConvertError`).
4. The provider asks the `Host` for the connection **now** (settings and key are read again at every call). It computes the digest of the address and the body: when the server refused that same request less than 30 seconds ago for a reason that retrying cannot fix, it throws that refusal again at once, without a call (the log line then has a code and no status). VS Code 1.147.0 retries every failure five times within about 15 seconds, whatever the extension throws (measured, D-025). Otherwise `transport.open` posts the body to `POST /ide/v1/chat/completions` with the key only in `Authorization`.
5. A non-2xx reply goes through `client.failureFromResponse` to a machine code. A 2xx reply is read by `sse.parseSse`: each `data:` chunk goes to `convert.ResponseReader`, which returns text at once and tool calls once complete (accumulated by `index`); an error event becomes its code; a stream that ends without `[DONE]`, or a connection that drops after the answer started, is `stream_truncated`.
6. Every part is reported to the editor as it arrives. The editor runs a tool call (with the user's approval) and, in the next request, sends the result back: step 1 again. A turn is normally two requests: the tool call, then the closing answer.
7. At the end `usage.prompt_tokens` calibrates `tokens` for this model; the provider writes one line (`call=chat`, alias, status, duration, token counts, tool-call count, machine code) through `Host.log`. A failure is thrown as a plain `Error` whose message is the sentence of the machine code (for `context_too_large` with numbers, `describeOverflow`), and a final refusal is remembered (step 4); a cancellation ends quietly. No other error kind changes the editor's retries (D-025). The editor's stop button never reached the extension on 1.147.0 (Ask, Agent, Plan, first and second turn): the cancellation path is wired and tested, but unused by that version.

Token counts asked by the editor (`provideTokenCount`) never leave the machine: `tokens` estimates from the characters. Measured on VS Code 1.147.0 (Lot X1d): the editor never called it in Ask, Agent or Plan; its new agent harness counts the prompt itself and compares it with `maxInputTokens`, so the input budget, not the estimate, decides whether Agent and Plan start.

## Data flow of one request of the chat panel

1. The user types and presses **Enter**. `media/panel.js` checks the length against the limit it was given, clears the input and posts `{type: "send", text}`.
2. `panel` hands the message to `session.receive`, which validates it with `protocol.parseWebviewMessage` (a message of any other shape is dropped; the log gets `call=webview dropped=1`).
3. `session` refuses a second request while one is open. It asks the host for the connection **now** (the same `resolve` as the provider: settings, discovery, key), then `conversation.beginTurn` adds the user's turn and an open answer; the conversation is saved in the background (`store.save`) and the webview gets the full state with the phase **Reading the request** and the time the request started.
4. `chat.streamChat` posts `conversation.requestBody` to `POST /ide/v1/chat/completions` through `transport.open`, with the `AbortSignal` of the request. The server sends its status and headers only with the runtime's first chunk, so until then nothing arrives: this is the phase **Reading the request**.
5. At the first event of the stream the phase becomes **Answering** (`first_ms` is measured). Each text delta is appended to the open answer; `session` sends the answer again to the webview at most every 50 ms (`render.renderBlocks` turns it into blocks) and saves it every 2 seconds.
6. **Stop**: the webview posts `{type: "stop"}`; `session` aborts the signal; `transport` destroys the request at once, so the connection closes and nothing more is read. The words received stay; the answer is marked stopped **while reading** or **while answering**, which chooses the sentence under it (`messages.PANEL`). The server's side of a stop is its own (D-100: the slot is freed at every stage on servers that have it).
7. At the end (complete, stopped or failed) `conversation.finishAnswer` records the outcome, the code and its overflow numbers, the usage and the durations; the conversation is saved; the webview gets the full state again. A failure is shown once, with the sentence of `messages.ts` (`describeCode`, `describeOverflow`): **no retry**, automatic or hidden. `chat` writes one log line (`call=chat`, status, `ms`, alias, token counts, `first_ms`, code).

## Data flow of one message with the panel's tools (Lot P0b)

1. When the user sends, `session` checks the tools: the host's workspace says `on` (a trusted window with a folder on the disk) and the chosen model reports tool calling. Otherwise the request is the plain chat above, and the panel shows why the tools are off (`ViewState.toolsNote`).
2. `agent.runAgent` sends step 1: `conversation.agentRequestBody` puts `tools.SYSTEM_PROMPT` first, then the conversation (with the steps earlier answers took), and `tools.TOOL_DEFINITIONS` in `tools`. `chat.streamChat` streams the text into the open answer and collects the tool calls; its log line carries `step=` and, when there are calls, `tool_calls=` and `tools=` (the extension's four names, `other` for any other).
3. An answer with calls: `conversation.recordCalls` moves the text so far and the calls into a step of the answer (`AssistantTurn.steps`); the phase becomes `tool` (**Using a tool**). Each call runs in order through `tools.runToolCall` against `workspace` (the real file system, read only, the folders of the window); its result, status and note are recorded and the panel shows the call's line. One log line `call=tool` per call: the tool's name, the outcome and, for a failure, its reason code.
4. `propose_edit` plans the change (`workspace.planEdit`) and, when it can apply, `session` waits for the user: the phase becomes `approval` (**Waiting for your decision**), the editor opens its diff view (`vscode.diff` between the file and a read-only virtual document), and the call's line shows **Show the change**, **Reject** and **Accept**. **Accept** asks the adapter to apply it: the document must be unchanged and saved, then `WorkspaceEdit` replaces the passage (or creates the file), the document is saved and shown. **Reject** leaves the file as it is; the model reads "Rejected by the user". The diff view is closed either way.
5. Step 2 sends the conversation again with the calls and one `tool` message per result. The loop ends at an answer without calls, at a failure (shown once), at **Stop** (no further call, no further step; a call that never ran gets the result "Not run: the user stopped the request." and the status stopped; a change that waits is not applied), or at 12 steps (the note under the answer says so).
6. The conversation (steps included) is saved after each step and at the end, in format 2.

## Data flow of the saved conversations

- **First show of the panel**: `session.start` asks `store.list` (the index, or the files when the index disagrees), opens the newest conversation and marks an answer it finds still open as interrupted (a window closed while it came), saving that change.
- **History** (the clock icon): the webview shows the list it receives in every state; opening an entry loads one file (`history.parseConversation`, strict), **Delete** asks the editor for a modal confirmation, then removes the file and its index entry. Both first wait for the saves already on their way.
- **A file that cannot be read** is listed without a title, never rewritten or removed, and opening it shows a sentence.
- **Where**: `panel` gives `store` the folder `conversations` of the extension's private storage for the workspace (`ExtensionContext.storageUri`), or of `globalStorageUri/no-folder` when no folder is open. The chosen model is kept in the workspace state.

## Data flow of the model list

The chat panel's list (Lot P0b): `extension.refreshStatus` sends one `GET /ide/v1/models` and gives the same promise to the status bar and to `session.refreshModels`, so the two no longer ask separately; the frozen provider still asks for its own. `session` keeps which models report tool calling.

`provideLanguageModelChatInformation` is called many times at start (six in a second, `silent` true). `ChatProvider.information` asks the `Host` for the connection, answers from the cache when it is under 60 seconds old, and otherwise joins the request already in flight or starts one (`client.getModels`). On success each entry becomes a model (`toModelEntry`: the alias as id, name and family, the output ceiling as `maxOutputTokens` and, as `maxInputTokens`, the window minus a reserve for the answer of an eighth of the window, at least 2048 tokens and never more than the ceiling (D-023; 28672 for a 32768-token model, unchanged for 131072), with a documented fallback of 8192 and 2048 tokens when the server does not say, tool calling and image input from the capabilities, the truth in the tooltip). On failure: surface off returns nothing and, when not silent, shows the administrator sentence once per address; a key needed offers **Set API Key**; a version mismatch says the two do not match; anything else keeps the last good list. `extension.refreshStatus` is the one place that reacts to a changed address, key or authority: it calls `ChatProvider.invalidate`, which clears the cache and fires `onDidChangeLanguageModelChatInformation`.

## Data flow of one connection check (Test Connection, or the status bar at start-up)

1. `extension` reads the four machine-scoped settings and calls `discoverServer` (`discovery`, which asks `platform` for the folder when nothing is configured and reads `server.env` afresh: nothing is cached, so a moved address or port is seen at the next check). The outcome is a target (`url`, `caFile`) or a reason why none was found (`messages` turns the reason into a sentence).
2. `keys.readKey` fetches the key for that URL from the secret store.
3. `client.checkConnection` calls `transport.open` for `GET /health`, then for `GET /ide/v1/models`. `transport` builds the headers (`Authorization` only when a key is set), loads and validates the authority file for HTTPS, applies the timeout and the cancellation signal, and returns the reply or throws a `CabinetError` (`unreachable`, `certificate_untrusted`, `timeout`, `cancelled`, a CA-file code).
4. A non-2xx reply goes through `failureFromResponse` (404 on `/ide/` is `ide_surface_off`, 401 is `key_needed`, otherwise the envelope's code, then the status). A 2xx body of the model list goes through `parseModels` (`ide_api` must be 1, unknown fields are ignored, a missing `features` is fine).
5. Each call reports `{call, status, durationMs, code}` to `log`, which writes the line to the output channel.
6. `messages.formatReport` builds the dialog text; `client.stateFromCode` picks the status-bar label.

## The stub gateway

`test/stub-gateway/stub.ts` is a plain `node:http(s)` server that speaks `/health` and `/ide/v1` with scripted answers: three models (`cabinet-chat` with tools; `cabinet-code` with tools and vision; `cabinet-plain` with neither) and modes `version-mismatch` (`ide_api: 2`), `off` (404), `key-needed` (401), `oversize` (a body above the cap), `redirect` and `small-model` (like `ok`, plus `cabinet-small`: window 32768, ceiling 16384, tools, no vision, the shape of a real server's code models; it is kept out of the default list so that the tests that count three models stay as they are). `npm run stub` starts it for demonstrations (`--mode`, `--port`, `--key`, `--https FOLDER`) and prints one console line per chat request and per answer's end through the stub's `onChat` option (a number, the scenario, the refused code, the model, the count of tools, the duration and whether the answer was sent to its end; never text), which is how the editor's retries and stops were counted. `test/support/pki.ts` builds a throw-away certificate authority with `node:crypto` only, for the HTTPS tests and the demo.

A chat request picks its script, first match wins, with (1) the body field `stub_scenario` (the contract says unknown fields are ignored; the connection tests use it), (2) a marker `[stub:<scenario>]` in the text of the last real user message (a user message that does not directly follow a tool message), which is how a person chooses from the chat box because the real provider sends no such field, (3) `text`.

## Tests

Run on the compiled output with Node's built-in runner (`npm test`); none needs VS Code or the outside network. Besides the unit tests of every module there are:

- **Golden requests** for the conversion (`test/fixtures/convert/*.json`: an Ask turn, an Agent turn with parallel calls and multi-part results, a Plan turn, a turn starting System, User, User, an image turn, a tool-result image), written with ASCII escapes only.
- **Provider tests** with a fake `Host` (`test/support/fake-host.ts`) against the stub and a hand-written server (`test/support/fake-server.ts`): the model list, caching, coalescing, every failure, every error code, cancellation, timeout, calibration. ## Where to add a feature

- **Something the panel shows or a button:** a field of `protocol.ViewState` or a new message type (validated in `parseWebviewMessage`, with a test), its text in `messages.PANEL`, the logic in `session` (with a test in `test/session.test.ts`), the drawing in `media/panel.js` (with `createElement` and `textContent` only; the guard of `test/panel-guards.test.ts` forbids the rest).
- **A new kind of block in the model's text:** `render` (a new `Block` or `Inline` kind, a test with hostile input), then its drawing in `media/panel.js`.
- **Something saved with a conversation:** a field of `conversation.AssistantTurn`, read back in `history.readTurn` (strictly; an unknown value is dropped), with a round-trip test; a change that an older version could not read raises `HISTORY_FORMAT`.
- **A new tool of the panel:** its definition, argument check and runner in `tools` (the neutrality guard of `test/tools.test.ts` reads every text the model sees), any file rule in `workspace` (pure, with a test on a real temporary folder), its name in `log.LOG_TOOL_NAMES` and its failure reasons in `log.LOG_TOOL_REASONS` (a guard compares them), its icon in `page.TOOL_ICONS` and its verb in `messages.AGENT_PANEL`, then its line in `session.viewCall`. A tool that writes goes through the user's decision and the editor's `WorkspaceEdit` in `extension`, never `node:fs`.
- **The loop's limits:** `agent.MAX_STEPS`, and the read, list and search bounds at the top of `workspace` (the README gives the numbers).

- **A new server call:** a function in `client` using `transport.open`; map its failures with `failureFromResponse`; add its sentences to `messages` (a new code goes in `codes` first, and the type system then demands a sentence); extend the stub additively; add `CallName` to `log` if it is a new kind of call.
- **A new kind of content in a chat message** (a new part type of the editor): `convert.classify` and the `convertUser` / `convertAssistant` branch that should carry it, a golden fixture in `test/fixtures/convert/`, and, for a refusal, a `ConvertReason` with its sentence in `messages` (an unknown part is refused, never dropped silently).
- **The input budget or the output ceiling reported to the editor:** `toModelEntry` in `provider` (one rule, decision D-023), with `test/provider-budget.test.ts`. Measure on the editor version in use first (lessons 15 and 17): the editor counts the prompt itself.
- **Which refusals the editor's retries should not reach the server:** `isFinalRefusal` in `provider` (decision D-025), with `test/provider-refusals.test.ts`. Throwing another error kind does not stop the retries on VS Code 1.147.0 (measured); measure again on a new editor version before changing the approach.
- **A new chat option** sent to the server: `convert.buildChatRequest` (only a known key, only when well formed), with a test in `test/convert.test.ts`.
- **A new model-facing tool** (X2a, X2b): a module `tools` that registers it, behind the context keys of the manifest; tool names must match `^[A-Za-z0-9_.:/-]{1,128}$`, and a guard sits beside every string the model sees.
- **A new stub scenario:** add it to `Scenario` and `SCENARIOS` in the stub, describe it in the header comment and in the table above, and give it a test in `test/stub-scenarios.test.ts`.
- **A new platform:** a branch in `platform.ts` and its tests; nothing else names a folder.
- **A new setting or command:** `package.json`, then the README (the drift test fails until both agree), then the adapter.
- **Anything that shows text to the user:** `messages.ts` only.
- **Anything that writes to the log:** add the field to `CallRecord` and to `formatCallLine`, with a shape check.
