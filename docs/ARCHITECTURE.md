# Architecture (completed lot by lot)

Status after Lot X1b: the connection layer and the model provider exist and are tested: the server's models appear in the chat and answer in Ask, Agent and Plan. The tools (`tools`) and the synced agents (`agents`) come in the next lots.

All sources are in `src/`, one job per module, zero runtime dependencies (only `node:` built-ins and the `vscode` types). Machine codes cross module boundaries; sentences exist only in `messages.ts`. Only `extension.ts` imports the editor: `convert`, `tokens` and `provider` run in plain Node and are tested without it.

## Modules

| Module      | Job                                                                                                                                                                                                                                                                                                                                         | Pure?                               |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| `codes`     | The closed list of machine codes (the contract's envelope codes plus the extension's own), `CabinetError` (its `message` is the code, never text) and the envelope-to-code mapping.                                                                                                                                                         | yes                                 |
| `platform`  | **The only module that names operating-system folders**: where `server.env` and `ca.pem` live on Windows and macOS. Platform and environment are arguments. A new platform is an added branch here.                                                                                                                                         | yes                                 |
| `discovery` | Turns the settings (and, if allowed, the text of the local `server.env`) into a target: URL, authority file, source. Parses `KEY=VALUE` tolerantly. Reads only `server.env`. `readTextFile` is the one function that touches the disk (read only, size capped).                                                                             | yes, except `readTextFile`          |
| `transport` | `node:http` / `node:https`. One keep-alive agent per server address (bounded to 8), no redirect followed, JSON bodies capped, streams not, no byte for N seconds is a timeout, cancellation through an `AbortSignal`, the authority file re-read and validated at each request.                                                             | no (network, authority file read)   |
| `sse`       | Incremental parser of the event stream: split lines, comments, `[DONE]`, error events and invalid JSON as typed errors that never hold the payload; a stream that ends without `[DONE]` is `stream_truncated`.                                                                                                                              | yes                                 |
| `client`    | Typed calls `GET /health` and `GET /ide/v1/models`, the status-to-code mapping (`failureFromResponse`), `ide_api` check, `checkConnection` for Test Connection, `stateFromCode` for the status bar.                                                                                                                                         | no (uses `transport`)               |
| `log`       | One content-free line per call from a closed list of fields; a value of the wrong shape is dropped.                                                                                                                                                                                                                                         | yes                                 |
| `keys`      | The API key in the editor's secret store, one per server address. `SecretStore` has the shape of `vscode.SecretStorage`.                                                                                                                                                                                                                    | yes (the store is an argument)      |
| `messages`  | Every sentence the user can read, one per machine code, plus the Test Connection report text, the notes added to what the model receives, the sentences of the conversion refusals and the model tooltip.                                                                                                                                   | yes                                 |
| `convert`   | The pure part of a chat call. Editor messages (role names, structural parts) to the server's OpenAI-shaped body (`buildChatRequest`); the server's stream chunks to the editor's parts (`ResponseReader`). Refusals are `ConvertError`s with a reason and no text. Imports nothing from the editor.                                         | yes                                 |
| `tokens`    | The token estimate behind `provideTokenCount`: characters over a ratio (starts at 3.0, so it errs high) plus a fixed amount per image, and the per-model calibration from `usage.prompt_tokens` (moving average, clamped to 2.0 to 6.0, a bounded table).                                                                                   | yes                                 |
| `provider`  | `ChatProvider`: the model list (cache of 60 s per address, concurrent calls coalesced into one request, last good list kept on failure, the right message for surface off, key needed, version mismatch), one chat request (conversion, stream loop, error mapping, one log line) and the token estimate. Works against an injected `Host`. | no (network through `transport`)    |
| `extension` | The thin VS Code adapter: registers the six commands, the status bar item, the output channel and the model provider, reads the settings, builds the `Host`, turns roles into names and plain parts into the editor's classes. No logic of its own.                                                                                         | no (needs VS Code; walked by owner) |

## Data flow of one chat request

1. The user sends a message. VS Code calls `provideLanguageModelChatResponse(model, messages, options, progress, token)` on the adapter in `extension.ts`.
2. The adapter changes what the editor's types cannot carry: each role number becomes its **name** (`User`, `Assistant` or `System`: the editor sends a System role that its type declarations do not list), the tool mode becomes `auto` or `required`, the cancellation token becomes an `AbortSignal`, and `progress` is wrapped so that plain parts become `LanguageModelTextPart` and `LanguageModelToolCallPart`.
3. `ChatProvider.chat` calls `convert.buildChatRequest`: roles by name, text parts joined, tool results into `tool` messages (an image of a tool result goes into the following `user` message, preceded by a note naming the tool), images into `image_url` data URLs, tools into function tools (a name the server would refuse is left out and counted), sampling options only when the editor sent a known key. An image for a model without vision, a role or a part that cannot be carried is refused here, **before anything is sent**, with a sentence from `messages` (a `ConvertError`).
4. The provider asks the `Host` for the connection **now** (settings and key are read again at every call), then `transport.open` posts the body to `POST /ide/v1/chat/completions` with the key only in `Authorization`.
5. A non-2xx reply goes through `client.failureFromResponse` to a machine code. A 2xx reply is read by `sse.parseSse`: each `data:` chunk goes to `convert.ResponseReader`, which returns text at once and tool calls once complete (accumulated by `index`); an error event becomes its code; a stream that ends without `[DONE]`, or a connection that drops after the answer started, is `stream_truncated`.
6. Every part is reported to the editor as it arrives. The editor runs a tool call (with the user's approval) and, in the next request, sends the result back: step 1 again. A turn is normally two requests: the tool call, then the closing answer.
7. At the end `usage.prompt_tokens` calibrates `tokens` for this model; the provider writes one line (`call=chat`, alias, status, duration, token counts, tool-call count, machine code) through `Host.log`. A failure is thrown as an `Error` whose message is the sentence of the machine code; a cancellation ends quietly.

Token counts asked by the editor (`provideTokenCount`) never leave the machine: `tokens` estimates from the characters.

## Data flow of the model list

`provideLanguageModelChatInformation` is called many times at start (six in a second, `silent` true). `ChatProvider.information` asks the `Host` for the connection, answers from the cache when it is under 60 seconds old, and otherwise joins the request already in flight or starts one (`client.getModels`). On success each entry becomes a model (`toModelEntry`: the alias as id, name and family, the window and output ceiling with a documented fallback of 8192 and 2048 tokens when the server does not say, tool calling and image input from the capabilities, the truth in the tooltip). On failure: surface off returns nothing and, when not silent, shows the administrator sentence once per address; a key needed offers **Set API Key**; a version mismatch says the two do not match; anything else keeps the last good list. `extension.refreshStatus` is the one place that reacts to a changed address, key or authority: it calls `ChatProvider.invalidate`, which clears the cache and fires `onDidChangeLanguageModelChatInformation`.

## Data flow of one connection check (Test Connection, or the status bar at start-up)

1. `extension` reads the four machine-scoped settings and calls `discoverServer` (`discovery`, which asks `platform` for the folder when nothing is configured). The outcome is a target (`url`, `caFile`) or a reason why none was found (`messages` turns the reason into a sentence).
2. `keys.readKey` fetches the key for that URL from the secret store.
3. `client.checkConnection` calls `transport.open` for `GET /health`, then for `GET /ide/v1/models`. `transport` builds the headers (`Authorization` only when a key is set), loads and validates the authority file for HTTPS, applies the timeout and the cancellation signal, and returns the reply or throws a `CabinetError` (`unreachable`, `certificate_untrusted`, `timeout`, `cancelled`, a CA-file code).
4. A non-2xx reply goes through `failureFromResponse` (404 on `/ide/` is `ide_surface_off`, 401 is `key_needed`, otherwise the envelope's code, then the status). A 2xx body of the model list goes through `parseModels` (`ide_api` must be 1, unknown fields are ignored, a missing `features` is fine).
5. Each call reports `{call, status, durationMs, code}` to `log`, which writes the line to the output channel.
6. `messages.formatReport` builds the dialog text; `client.stateFromCode` picks the status-bar label.

## The stub gateway

`test/stub-gateway/stub.ts` is a plain `node:http(s)` server that speaks `/health` and `/ide/v1` with scripted answers: three models (`cabinet-chat` with tools; `cabinet-code` with tools and vision; `cabinet-plain` with neither) and modes `version-mismatch` (`ide_api: 2`), `off` (404), `key-needed` (401), `oversize` (a body above the cap) and `redirect`. `npm run stub` starts it for demonstrations (`--mode`, `--port`, `--key`, `--https FOLDER`). `test/support/pki.ts` builds a throw-away certificate authority with `node:crypto` only, for the HTTPS tests and the demo.

A chat request picks its script, first match wins, with (1) the body field `stub_scenario` (the contract says unknown fields are ignored; the connection tests use it), (2) a marker `[stub:<scenario>]` in the text of the last real user message (a user message that does not directly follow a tool message), which is how a person chooses from the chat box because the real provider sends no such field, (3) `text`.

| Scenario     | What the stub does                                                                                                                                                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `text`       | A short streamed answer (the default).                                                                                                                                                                                                                                                                                    |
| `tool-call`  | Calls a tool **taken from the request's own `tools` list** (the one a marker such as `[stub:tool-call:create_file]` names, else the first whose name contains `read_file`, otherwise the first) with the smallest valid arguments; once a tool message follows the last real user message it answers with a closing text. |
| `error`      | An error event inside the stream, then `[DONE]`.                                                                                                                                                                                                                                                                          |
| `error-http` | `503 provider_unreachable`.                                                                                                                                                                                                                                                                                               |
| `slow`       | A late first byte.                                                                                                                                                                                                                                                                                                        |
| `split`      | The stream three bytes at a time, so a multi-byte character is cut.                                                                                                                                                                                                                                                       |
| `empty`      | The contract's `502 empty_answer`.                                                                                                                                                                                                                                                                                        |
| `long`       | A slow trickle of text for about a minute (for the stop button and cancellation).                                                                                                                                                                                                                                         |
| `cut`        | Two chunks, then the connection is destroyed (for "the server stopped mid-answer").                                                                                                                                                                                                                                       |

With `stream_options.include_usage` the stream ends with a usage chunk whose prompt tokens are the text characters of the request divided by four, so calibration can be tested. An image sent to a model whose `capabilities.vision` is false (`cabinet-chat`, `cabinet-plain`) is answered `400 provider_capability_unsupported`, like the server.

## Tests

Run on the compiled output with Node's built-in runner (`npm test`); none needs VS Code or the outside network. Besides the unit tests of every module there are:

- **Golden requests** for the conversion (`test/fixtures/convert/*.json`: an Ask turn, an Agent turn with parallel calls and multi-part results, a Plan turn, a turn starting System, User, User, an image turn, a tool-result image), written with ASCII escapes only.
- **Provider tests** with a fake `Host` (`test/support/fake-host.ts`) against the stub and a hand-written server (`test/support/fake-server.ts`): the model list, caching, coalescing, every failure, every error code, cancellation, timeout, calibration.
- **Guard tests** in `test/guards.test.ts`, `test/manifest.test.ts`, `test/provider-guards.test.ts` and `test/provider-leak.test.ts`: language (no French diacritics outside one named fixture), no-leak (a unique secret in the key, a message, a tool argument, a tool result, an image payload, a tool description and a role name never appears in an error, a log line, a message shown to the user or a file, in the connection path and in the provider path), no-network and no-risk (imports limited to an allow-list, no URL literal outside documentation links, no process spawning, no `eval`, no file writing, no `console`, no disabled certificate check), drift (the README names every command and setting and the package file of the current version), contract (`docs/IDE-CONTRACT.md` equals the server's copy when it is next to this repository), the manifest (identifiers, machine scope of every setting, the provider contribution, no `*` activation, no runtime dependency, exact dev versions), the pure modules (`convert`, `provider`, `tokens` import only relative modules) and the removed probe.

## Where to add a feature

- **A new server call:** a function in `client` using `transport.open`; map its failures with `failureFromResponse`; add its sentences to `messages` (a new code goes in `codes` first, and the type system then demands a sentence); extend the stub additively; add `CallName` to `log` if it is a new kind of call.
- **A new kind of content in a chat message** (a new part type of the editor): `convert.classify` and the `convertUser` / `convertAssistant` branch that should carry it, a golden fixture in `test/fixtures/convert/`, and, for a refusal, a `ConvertReason` with its sentence in `messages` (an unknown part is refused, never dropped silently).
- **A new chat option** sent to the server: `convert.buildChatRequest` (only a known key, only when well formed), with a test in `test/convert.test.ts`.
- **A new model-facing tool** (X2a, X2b): a module `tools` that registers it, behind the context keys of the manifest; tool names must match `^[A-Za-z0-9_.:/-]{1,128}$`, and a guard sits beside every string the model sees.
- **A new stub scenario:** add it to `Scenario` and `SCENARIOS` in the stub, describe it in the header comment and in the table above, and give it a test in `test/stub-scenarios.test.ts`.
- **A new platform:** a branch in `platform.ts` and its tests; nothing else names a folder.
- **A new setting or command:** `package.json`, then the README (the drift test fails until both agree), then the adapter.
- **Anything that shows text to the user:** `messages.ts` only.
- **Anything that writes to the log:** add the field to `CallRecord` and to `formatCallLine`, with a shape check.
