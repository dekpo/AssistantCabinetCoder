## What "agents" means here

A custom agent is a Markdown file with a YAML header (name, description, the tools it may use, optionally a model) and instructions. The editor lists it in the agents dropdown beside Ask, Agent and Plan and runs it with the model the user selected (or the one named in the file). Two sources, both explicit and visible to the user:

1. **Bundled agents**, shipped inside the `.vsix` (no server needed): a small default set, in English, neutral about who the user is, each a real working role for vibe-coding.
2. **Agents of the server**: the administrator's catalogue (`GET /ide/v1/agents`), copied into the workspace on the user's command, because a stable extension cannot register agents dynamically.

## Build

1. **Bundled agents** `agents/*.agent.md` and, if the spike's (f) shows it works in a sideloaded stable `.vsix`, `contributes.chatAgents: [{ "path": "./agents/<file>" }]` for each. Write five, each with `name`, `description`, `tools` (only names the spike's (i) recorded as real; read-only roles get read/search tools only; an implementer gets edit and terminal tools; **no `model:` field**, so the agent uses whichever Assistant Cabinet Coder model is selected) and instructions of 15 to 40 lines: **Cabinet Implementer** (small verified steps: read first, change the minimum, run the tests, report what changed), **Cabinet Reviewer** (read-only: correctness, security, tests; findings ordered by severity with file and line), **Cabinet Architect** (read-only: proposes a design and a plan with trade-offs and asks before assuming), **Cabinet Debugger** (reproduce, hypothesise, verify, fix the root cause), **Cabinet Test Writer** (tests first, no production change unless asked). The instructions are written for an open-weight model driving the editor's tools: short imperative sentences, explicit "use the tools, do not paste file contents back", explicit stop conditions, no flattery, no mention of any profession or organisation. Each has a test that its tool names exist in the recorded list and that its text contains none of the words `patient`, `doctor`, `practice`, `client`, `lawyer` (the repository's neutrality rule, kept here as a guard test next to the files).
2. **Command `Assistant Cabinet Coder: Sync Agents From Server`** (`assistantCabinetCoder.syncAgents`; absent from the palette unless the context key `assistantCabinetCoder.agents` is true, set from the server's `features.agents`). `GET /ide/v1/agents` (the server must report `features.agents`; otherwise a clear message). Show a multi-select quick pick of the entries (name, description, model, tools) and, for the chosen ones, a **preview** (a read-only virtual document with the exact file that will be written). Write `<workspace folder>/.github/agents/cabinet-<id>.agent.md` (ask which folder when several are open; refuse when none is open). The file is generated by code, never copied from the server: YAML header with every value emitted as a double-quoted, escaped scalar (`name`, `description`, each tool; refuse any value with a line break or a control character), `model:` only when the entry has an alias, written in the form the spike's (f) recorded for the picker name (if the spike could not establish the form, omit `model:` and say so in the README), `user-invocable` from the entry; the body is the instructions with a first line `<!-- managed by Assistant Cabinet Coder; do not edit; server catalogue id: <id> -->`. The file name comes **only** from the validated id pattern (`^[a-z0-9][a-z0-9-]{0,47}$`), never from any other server text; the target path is checked to stay inside `.github/agents`. **Never overwrite a file that lacks the managed marker** (offer to skip), and ask before overwriting a managed one whose content differs from what would be written (show both). Nothing is deleted except by the separate command `Assistant Cabinet Coder: Remove Synced Agents` (`assistantCabinetCoder.removeSyncedAgents`: lists the managed files, asks, removes only files that carry the marker).
3. **Git hygiene.** After a sync, if the folder is a git repository, offer once (a notification with buttons, remembered in the workspace state) to add `.github/agents/cabinet-*.agent.md` to `.git/info/exclude` (the local, uncommitted exclude file; never `.gitignore`, never a commit). Never run a git command: edit that one file with `fs`, appending the line if absent.
4. **Update hint, never an automatic write.** When the extension connects and the server reports agents, compare a hash of each managed file's would-be content with the file on disk and show a quiet status-bar hint "N agent updates" that runs the sync command; nothing is written without the user.
5. **Tests.** Header generation and escaping (quotes, colons, unicode, a value with a newline refused, a very long value refused); file name and path-traversal cases; marker rules (overwrite, skip, remove); preview equals written bytes; `model:` form from a recorded fixture; bundled files validated (parse the YAML header with a tiny pure parser written in the tests, names in the recorded tool list, neutrality guard); the quick-pick flow with the VS Code adapter faked; the git exclude edit (idempotent, no `.git` means no offer); the command is absent from the palette when the server lacks `features.agents`; no-leak (a unique secret in an agent's instructions never reaches the log); the write-scope test (the only paths this module can write are under `.github/agents/` and `.git/info/exclude`).
6. **Docs.** README (the two sources, what a synced file looks like, where it goes, how to remove it, the honest limit that a stable extension cannot add agents dynamically so the user runs the sync command), `docs/ARCHITECTURE.md`, `docs/human-tests/X3-agents.md` (at most about 25 minutes): the bundled agents appear in the dropdown; run the Reviewer on a small change and check it edits nothing; sync, preview, write, edit the catalogue on the server and see the update hint; remove; check that a hand-made file with the same name is never overwritten.
