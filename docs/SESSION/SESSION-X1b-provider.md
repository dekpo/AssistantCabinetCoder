## Facts from the owner's real runs that bind the design (copied here so they are not missed)

From `docs/SPIKE-FINDINGS.md`, "Consequences for the next lots", X1b:

1. **A System role arrives at runtime** although `@types/vscode` 1.140.0 declares only User and Assistant, and its numeric value was not recorded. The adapter therefore maps the role by its **name** (`vscode.LanguageModelChatMessageRole[role]` gives `"User"`, `"Assistant"` or `"System"`) and hands `convert` a role name, never a number; an unknown name is refused with a clear message. A System message becomes a `system` message. The request of every mode begins System, User, User (15 000 to 19 000 characters of system text), so a model needs a window of 32 768 tokens or more.
2. `provideLanguageModelChatInformation` is called many times at start (6 calls in a second, `silent` true): answer from a cache **and** coalesce concurrent calls into one request in flight.
3. Every mode sends tools, so a model without tool calling is never usable in the chat (VS Code does not even list it). List every model the server reports anyway, with the truth in its tooltip.
4. The history, images included, is replayed in every request. The server caps images per request (default 8) and per image (default 8 MiB): when it answers `payload_too_large`, the message says so; **no image is dropped silently**.
5. A pasted or attached image arrives as one `image/png` data part (the editor may re-encode it); a text file, a selection and a PDF arrive as **text only**.
6. A tool result may hold a data part (image) plus a text part (added by the editor).
7. `modelOptions` holds only private `_...` keys, no sampling parameter: send none unless a known key (`temperature`, `top_p`, `stop`) is present.
8. Exactly 2 requests per turn (the tool call, then the closing answer); no hidden title or summary request.
9. The provider tab in the picker shows the vendor `displayName`; the model line shows the `name`; the tooltip is the detail.

## Build

**Manifest.** Add `contributes.languageModelChatProviders: [{ "vendor": "assistantcabinetcoder", "displayName": "Assistant Cabinet Coder", "managementCommand": "assistantCabinetCoder.manage" }]`. **No explicit activation event is added:** VS Code generates `onLanguageModelChatProvider:assistantcabinetcoder` from the contribution by itself (spike, pre-run evidence), and the extension already activates at start-up (D-010). The provider is registered in `activate`. Version: set `0.2.0` (practice 9 of `VIBE-CODING-PRACTICES.md`: every installed build has a new version number), and update the README's package file name; the manifest test of X1a pins the version, so its expected value is the first named exception.

**Structure that keeps the logic testable without VS Code.** `vscode` classes (`LanguageModelTextPart`, `LanguageModelToolCallPart`, ...) exist only inside the editor, so a module that imports them at run time cannot be loaded by `node --test`.
- `convert.ts` and `tokens.ts` import **nothing** from `vscode`, not even as a value. They work on small structural types written in the module (a text part has a string `value`; a tool-call part has `callId`, `name`, `input`; a tool-result part has `callId` and a `content` list; a data part has `mimeType` and `data`) and on plain role names. They return plain objects (for example `{ kind: "text", value }`, `{ kind: "toolCall", callId, name, input }`).
- `provider.ts` holds the logic of the provider (cache, coalescing, silent handling, request, stream loop, error mapping, token count) against an injected `Host` interface: how to resolve the connection (`{options, target}` as `extension.ts` does today, read at **each** call so a new key or address applies at once), how to read the stored key, how to show a message or offer an action, how to build and report the editor's own part objects, how to fire the change event, how to log. `provider.ts` therefore needs no `vscode` import either; the real `Host` is built in `extension.ts`, which stays thin. Everything in `provider.ts` is tested with a fake `Host` against the stub.

**`provider.ts` - `provideLanguageModelChatInformation`.** Calls `client.getModels` (unchanged). `ide_surface_off`: with `silent` true return no models; with `silent` false show once (per session and address) the administrator sentence of `messages.ts`. `key_needed`: with `silent` false offer **Set API Key**. `ide_api_mismatch`: show "this extension and this server do not match" (new sentence in `messages.ts`). Any other failure: `silent` true returns the last good list or none; `silent` false shows the sentence of its code. Map each entry (`ModelInfo` from X1a: `contextWindow` and `maxOutputTokens` can be `undefined`, so choose and document a fallback, for example 8192 and 2048, and tell it in the tooltip): `id`, `name` and `family` = the alias, `version: "1"`, `detail: "Assistant Cabinet Coder"` (a name constant in `messages.ts`), `tooltip` = window, output ceiling, tools and vision yes/no, `maxOutputTokens` = `max_output_tokens`, `maxInputTokens` = `context_window - max_output_tokens` (never below 1), `capabilities: { toolCalling: capabilities.tools, imageInput: capabilities.vision }`; ids sorted as the server sorts them. Fire `onDidChangeLanguageModelChatInformation` when the address, the key or the authority changes: `extension.ts` already reacts to the three commands and to the settings in one place (`refreshStatus`); add the firing and the cache clearing there, nowhere else. Cache 60 s; a failed refresh keeps the last good list; the cache holds one entry per server address and is bounded.

**`src/convert.ts` - the pure part of `provideLanguageModelChatResponse`** (the bulk of the tests). Editor messages -> OpenAI messages, in order. A `User` message's text parts become one `user` message; each tool-result part becomes a `tool` message (`tool_call_id` = `callId`; content = the result's text parts joined; a result part that is an image cannot ride in a tool message, so the image goes into a **following `user` message** as an `image_url` part with a `data:` URL, preceded by one short English text part naming the tool, kept in `messages.ts`; a result part of another kind is replaced by a short note, never dropped silently); a user message mixing text and tool results becomes the tool messages first, then the text; an `Assistant` message's text becomes `content` (or `null`) and its tool-call parts become `tool_calls` with `arguments = JSON.stringify(input)`; a data part with a mime type of `image/png`, `image/jpeg`, `image/webp` or `image/gif` in a user message becomes an `image_url` part (`data:<mime>;base64,...`), any other data part is refused with a clear message; an image sent to a model whose `capabilities.vision` is false is refused **before** sending, with a message; a `System` message becomes `system`. Where the findings (c), (d), (e) show that the editor hands over something different from the above, follow the findings and write the difference in `docs/DECISIONS.md`. `options.tools` -> OpenAI function tools (name, description, `inputSchema`; names must match the contract's pattern, an unusable tool is left out and counted, not logged by name); `toolMode` Auto -> `tool_choice: "auto"`, Required -> `"required"` (the server accepts and ignores it: the README states the limit). Request body: `stream: true`, `stream_options: { include_usage: true }`, `model` = the alias, no `max_tokens`, and `temperature`, `top_p`, `stop` only when given.
Responses: text deltas are reported as they arrive; tool-call deltas are accumulated by `index` (the server sends calls whole, a client must still accept split calls) and reported once complete, with `input` = the parsed `arguments` (must be an object; empty means `{}`); invalid JSON in the arguments is an error that **may name the tool only when its name is in the request's own tool list and matches `^[A-Za-z0-9_.:/-]{1,128}$`, and never shows the arguments**; an error event or a non-2xx status becomes a message from the **machine code only** (`context_too_large`, `server_busy`, `empty_answer`, `provider_capability_unsupported`, `payload_too_large`, `rate_limited`, ...: every code already has its sentence in `messages.ts` since X1a; add only what is new, such as the sentences above). The stream loop uses `parseSse` (X1a) over `transport.open(...).chunks()` and `client.failureFromResponse` for non-2xx replies; a stream that ends without `[DONE]` is `stream_truncated`. Read `usage` when present. The conversion never writes or logs any of the content it handles.

**`src/tokens.ts` and `provideTokenCount`.** `ceil(characters / ratio)` over text parts, tool-call arguments and tool-result text (+ a fixed estimate per image, a named constant), ratio starting at 3.0 and **calibrated per model** from `usage.prompt_tokens` against the characters of the request that produced it (exponential moving average, clamped to 2.0 to 6.0; one table entry per model, bounded). The editor prunes the conversation with this number, so the estimate errs high. Never calls the network.

**Logging.** The chat call logs one line through `log.ts` (`call=chat`, alias, status, duration, prompt and completion tokens, tool-call count, machine code), never text. The fields already exist.

**The stub gateway (additive; the existing stub and its test stay as they are).** Before `spike/` is deleted, port from `spike/src/script.ts` the logic that is worth keeping into `test/stub-gateway/` (the minimal arguments for a tool's required properties, the choice of the tool to call). Then add: (1) **scenario selection without the body field.** The real provider sends no `stub_scenario`, so the human test could not choose a script; the stub also reads a marker `[stub:<scenario>]` in the text of the last user message (and keeps the body field, which the X1a tests use); (2) a `tool-call` scenario that calls a tool **taken from the request's own `tools` list** (the first whose name contains `read_file`, otherwise the first), with minimal arguments, and a closing text answer when the last message is a tool result, so Ask, Agent and Plan show the loop the spike recorded; (3) a `usage` chunk when `stream_options.include_usage` is true (token counts that depend on the request size, so calibration can be tested); (4) an `empty` scenario (the contract's `empty_answer` 502); (5) a `long` scenario (a slow trickle of text for about a minute) for the stop button and cancellation; (6) a `cut` scenario (the connection is destroyed after a few chunks) for "server stopped mid-answer"; (7) the vision check: a request with an image to the model `cabinet-plain` answers `provider_capability_unsupported` 400 like the server does. Document the markers in the stub's header comment and in `docs/ARCHITECTURE.md`.

## Lessons that bind this lot

- **Lesson 3:** the writing tool turns Unicode escape sequences into real accented characters. After writing any source or fixture, run `grep -nP '[^\x00-\x7F]' -r src test`; golden fixtures are scanned by the language guard too (`.json` under `test/`), so they are pure ASCII with escapes. Documents describe such characters in words.
- **Lesson 4:** a guard reads comments. Never quote `eval`, `fetch(`, `console.`, `rejectUnauthorized`, a process-spawning module or a file-writing call in a comment of `src/`.
- **Lesson 2 and 5:** in the human test, name an on-screen item only as it appears on a screenshot of this VS Code (the X1a run record has real ones: dialogs, the status bar, the quick pick), and read the code of every dialog the extension opens before writing a step that uses it. Ask the owner for a screenshot rather than guess a label for the chat picker.
- **Lesson 6:** the clean-up part of the human test starts by closing the test window and saying how to know it is closed; no check runs before that.
